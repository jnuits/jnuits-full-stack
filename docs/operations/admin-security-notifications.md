# Admin security notices and recommendations

Status: implementation and acceptance in progress; Release 3 is not deployed and its migration is unapplied. Email delivery remains disabled.

Local acceptance on 2026-10-16 passed 2,583 tests across 383 files, lint/typecheck, access/UI/dependency/credential checks, all 123 migrations in clean replay with generated types and database lint/advisors, and a production build. Combined disposable browser acceptance passed all 46 existing/new scenarios, including 16 notification cases in Chromium/WebKit. The final review's three delivery/permission/priority regressions have failing-then-passing test receipts. Linux three-engine CI, hosted SQL parity and actual deployment smoke remain release gates; local results do not certify production email delivery.

Release 3 extends the existing one daily accountability job. Panel notices use current active-admin and audit permissions; the inbox and optional preferences never grant audit access. Each notice belongs to one recipient. A permission change is checked again before read or delivery. New email preferences default off. Own preferences live under My Admin Profile and do not need global settings permission.

Committed application changes attempt their panel projection in the same transaction; a notice failure cannot block the completed business action. The daily collector recovers missing notices. Native-provider notices arrive after collection. The inbox also shows a permission-checked job health receipt, last finished/successful times, backlog and uncertain-delivery count. A notification failure preserves the independently recorded native audit coverage; a dry run does not write a successful-job receipt.

Provider-owned account-holder password/MFA security mail remains separate from optional peer mail. The owner confirmed Supabase's Password changed notice enabled; actual mailbox acceptance remains owner-operated. The application never sends an own-account password/MFA copy through the peer channel. Native MFA enrollment needs the exact provider factor/setup/first successful verification identities after cutover. Setup, cancelled/unverified removal, ordinary re-verification and unknown prior setup do not announce a new factor. Auth schema, provider configuration and real roles are unchanged.

Notice and delivery activation cutovers prevent historical broadcasts. Durable source/recipient/channel and account/month identities survive detail cleanup. A rubric version is frozen metadata, not a new monthly send key. Empty, unavailable, inactive or opted-out accounts receive no newly generated recommendation email. Suggestions use the shared completion rubric, current account-level factor state and permitted queues; no browser AAL, XP, productivity ranking or absence-of-login inference is invented.

Delivery is **disabled by default** in the private controls. Before activation, run `node scripts/validate-env.mjs --production --admin-delivery` in the privately configured production environment, capture provider quotas, test verified-address/suppression/bounce/complaint/replay behavior, and complete the owner's consenting-mailbox acceptance. This preflight does not enable delivery. Keep native collection independently operational when mail is disabled.

On 2026-10-16 the connected provider account listed the verified `jnuits.org.bd` sending domain. Read-only usage was 0/100 daily emails and 20/3,000 monthly emails, with daily reset at 23:59:59.999 UTC and monthly reset 2026-11-06 08:53 UTC. This is a snapshot, not a capacity reservation; password resets and invitations take precedence. The job permits at most ten sends and one provider request per second inside its existing 20-second work budget. No paid service or second schedule is introduced.

Provider-controlled rehearsal on 2026-10-16 used only the [documented Resend test recipients](https://resend.com/docs/dashboard/emails/send-test-emails): delivered receipt `01a143ef-b215-739f-a028-a85af90932fe`, bounced receipt `01a143ef-e3ce-79b9-8296-048b49bb75d0`, complained receipt `01a143f0-8077-78b1-9a26-6f71bc546cb7`. A repeated identical delivered request returned the same message ID under the original idempotency key. These three test sends consume provider quota; they do not prove real mailbox placement or the unreleased application webhook's production handling. Disposable application acceptance separately verifies signed webhook replay, suppression and durable delivery-state transitions. Owner mailbox acceptance and production activation remain open.

Frozen payloads, atomic leases, stable provider idempotency keys and current-recipient checks guard retries. Provider acceptance is `accepted`; only a verified delivery webhook establishes `delivered`. A lost accepted-response write leaves an uncertain leased record. A previously uncertain attempt cannot be blindly retried at or beyond Resend's 24-hour window (a one-minute margin applies), even if a later response was rate-limited. Operator reconciliation must resolve such records without repeating the underlying password/invitation action. Bounce/complaint/suppression receipts block later optional sends and are never automatically removed.

Expired uncertain records remain visible for operator reconciliation and do not occupy the next delivery batch. Security deliveries run before optional monthly account evaluation; the second phase handles recommendation mail only, sharing the ten-send limit and provider pacing. An uncertain security attempt is reconsidered by a later job rather than retried in both phases of one job. Frozen recommendation IDs preserve the permission requirements of included duty counts; those permissions are checked again at claim and immediately before sending. Revoked queue permission suppresses that frozen email rather than leaking a previously authorized count.

The operator script defaults to a dry run and never sends from that preview. `--apply` runs the enabled job policy: after explicit activation it may enqueue and send optional emails. Its sanitized `sends` counter means provider acceptances, not proven deliveries. It never prints recipient addresses or credentials. Job credentials belong in private environment configuration, never query strings or command arguments. Keep important details for at least three calendar months and durable replay keys beyond cleanup; all purge activation and earlier backup/recovery acceptance gaps remain separate.
