# Admin activity retention

Important activity/security details in the new private projection have at least three calendar months in Asia/Dhaka from **both** occurrence and ingestion. An old event imported today receives a fresh three-month minimum. Incident holds exclude the affected records. Existing legacy application audit and private verification history are not shortened. Compact non-network summaries survive for the account lifetime, and expire only three months after permanent removal, with no incident hold and no live account; a freeze is not removal. Durable source keys and identity/checkpoint evidence survive cleanup, so replay does not resurrect expired details or notices.

The owner's 2026-10-15 refinement gives routine Auth records a 30-day policy. The initial narrow allowlist contains only `token_refreshed`. Login/logout, passwords, MFA, identities and unknown/future action types are retained; they are not silently classified as routine. Older pre-cutover provider history remains untouched. A refresh row for a known admin cannot be removed before its normalized durable receipt exists. Incident holds also apply. No Auth tables, indexes, policies or triggers are created/altered, and API-role Auth grants are unchanged.

On 2026-10-15 a read-only hosted privilege check confirmed the existing `postgres` connection has SELECT/DELETE on `auth.audit_log_entries`, owned by `supabase_auth_admin`, with no non-internal triggers or referencing foreign keys observed. Optional deletion uses those existing privileges in a service-only function; it never grants browsers Auth access. The disposable replay tests this against actual Supabase Auth. No hosted purge has run.

Both cleanup switches default **off**. Before activation, use service-only `preview_admin_activity_retention()` and `preview_routine_auth_retention()`; capture the production revision, cutoffs, safe counts, collection receipts and incident-hold review. The routine preview is bounded to 501 candidates; it is not a full-table total. Review the production dry-run and explicitly activate the respective private policy only after it is accepted. Do not infer activation from a code deployment. The current collection-only job does not run purge while these policies await activation.

`purge_expired_admin_activity(limit)` and `purge_routine_auth_retention(limit)` each accept 1–500 rows and are service-only. Unactivated calls fail closed. Process bounded batches, retaining receipts and recording safe counts. Do not add an independent schedule or use broad ad hoc deletes. Retention activation/automation remains a separate operator release step after the reviewed first production preview; this document does not claim 30-day cleanup is already active.
